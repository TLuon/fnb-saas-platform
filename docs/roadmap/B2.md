# B2 - Backend Business Flow và API hoàn thiện

## 1. Vai trò

B2 là người chịu trách nhiệm làm backend nghiệp vụ hoàn thiện để bàn giao cho frontend. B2 sử dụng schema, RLS, guard và common infrastructure do B1 quản lý; không tự ý thay đổi database chung. Nếu cần dữ liệu mới, B2 gửi yêu cầu schema cho B1 kèm use case, field, index, RLS và lý do lưu Postgres thay vì Redis.

## 2. Phạm vi sở hữu

- Reservation và payment mock.
- Redis reservation lock.
- Order/POS.
- KDS và kitchen status.
- Group-order Redis session.
- Wallet.
- Coffee Pass.
- Support/CSKH.
- Unmatched transactions.
- Maker-checker.
- CSAT.
- Socket.IO events cho nghiệp vụ.
- Audit log cho financial mutation.
- API collection và integration test để bàn giao cho F1/F2.

## 3. Nguyên tắc triển khai

- Không dùng service role cho request nghiệp vụ thông thường.
- Mọi query dùng JWT user và RLS, trừ thao tác hệ thống đã được thiết kế rõ.
- Mọi tổng tiền phải tính/kiểm tra lại ở backend.
- Mọi payment phải idempotent.
- Lock bàn phải atomically kiểm tra ownership và TTL.
- Không đánh dấu paid/completed dựa riêng vào callback frontend.
- Không lưu session group-order tạm vào Postgres nếu Redis đã đủ.
- Mọi lỗi phải dùng error code canonical.
- Mọi API phải có DTO validation, auth guard, role guard và test.

# P1 - Reservation và Payment API

## 1. Lock bàn

### `POST /api/v1/reservations/lock`

- Role: `CUSTOMER`.
- Nhận `table_id`.
- Kiểm tra table thuộc tenant/branch hợp lệ.
- Kiểm tra table đang `AVAILABLE`.
- Tạo reservation code duy nhất.
- Redis `SET NX EX` với TTL 10 phút.
- Nếu lock thất bại trả `ERR_2002_TABLE_LOCKED`.
- Cập nhật table `AVAILABLE -> PENDING_LOCK` theo transaction/rule.
- Trả `reservation_code`, `expires_at`, `deposit_amount`, `table_id`.
- Lưu token owner theo cách không làm lộ dữ liệu nhạy cảm.

### `POST /api/v1/reservations/:code/generate-qr`

- Role: `CUSTOMER`.
- Kiểm tra reservation thuộc token/user hiện tại.
- Trả QR payload, code và amount.
- Không để client tự thay đổi amount.

### `DELETE /api/v1/reservations/:code`

- Role: `CUSTOMER`.
- Chỉ owner của lock được hủy.
- Compare-and-delete Redis key.
- Đưa bàn `PENDING_LOCK -> AVAILABLE`.
- Nếu hết hạn trả `ERR_3001_RESERVATION_EXPIRED`.

## 2. Payment webhook

### `POST /api/v1/reservations/webhook/mock-payment`

- Public mock route nhưng bắt buộc secret ở môi trường production/staging.
- Validate raw transfer content và amount.
- Resolve tenant rõ ràng.
- Đối chiếu reservation code.
- Tạo payment transaction.
- Idempotency database chống duplicate webhook.
- Match thành công:
  - [ ] Chuyển payment completed.
  - [ ] Chuyển bàn `PENDING_LOCK -> RESERVED`.
  - [ ] Giải phóng lock.
  - [ ] Emit `table_status_changed`.
- Match thất bại:
  - [ ] Tạo `unmatched_transactions`.
  - [ ] Emit `unmatched_transaction_created`.
  - [ ] Trả error code đúng.
- Rate limit mock webhook.
- Không log secret hoặc token.

## Tiêu chí nghiệm thu

Hai customer cùng lock một bàn: chỉ một request thành công. Webhook gửi hai lần không tạo payment/reservation duplicate. Webhook sai code tạo unmatched transaction.

# P2 - Order/POS API

## 1. Tạo order

### `POST /api/v1/orders`

- Role: `STAFF`.
- Nhận `table_id`, reservation code nếu có, order type.
- Kiểm tra table/reservation.
- Lock row/table để chống check-in trùng.
- Tạo order code.
- Chuyển bàn sang `OCCUPIED` theo state machine.
- Liên kết `current_order_id`.
- Áp dụng deposit đúng một lần.
- Trả order summary.

## 2. Order detail

### `GET /api/v1/orders/:id`

- Role: `STAFF`, `CUSTOMER`, `OWNER` theo ownership.
- Trả order, items, modifiers, subtotal, discount, final amount, status.
- Customer chỉ được đọc order của mình.

## 3. Order items

### `POST /api/v1/orders/:id/items`

- Role: `STAFF`, `CUSTOMER` theo flow.
- Nhận product id, quantity, modifiers.
- Kiểm tra product active.
- Snapshot tên/giá cần thiết để order không bị thay đổi lịch sử khi menu đổi.
- Tính lại tổng backend.
- Reject quantity âm/zero.

## 3A. Danh sách order của Customer

### `GET /api/v1/orders?page=&limit=`

- Role: `CUSTOMER`, `STAFF`, `OWNER` theo permission matrix.
- Với Customer, luôn lấy customer id từ JWT, không nhận `customer_id` tùy ý.
- Trả danh sách order của chính customer, phân trang và filter status.
- Đây là API cho F2 xây `/orders`; không để frontend tự dựng lịch sử từ Zustand.

## 3B. KDS snapshot

### `GET /api/v1/orders/kds?branch_id=&station=&status=`

- Role: `STAFF`.
- `station` chỉ nhận `BAR` hoặc `KITCHEN`, lấy từ category/product; đây không phải role mới.
- Trả các order item đang `QUEUED`, `PREPARING`, `READY` theo branch.
- Đây là snapshot khi F1 mở trang hoặc reconnect Socket.IO.
- Query phải giới hạn branch/tenant bằng JWT và RLS.

### `PATCH /api/v1/orders/:id/items/:itemId`

- Role: `STAFF`, `CUSTOMER` trước khi submit kitchen.
- Không cho sửa item đã vào trạng thái không phù hợp.
- Tính lại tổng.

### `POST /api/v1/orders/:id/submit-kitchen`

- Role: `STAFF`.
- Reject order rỗng bằng `ERR_4003_EMPTY_ORDER_SUBMIT`.
- Tách item theo `BAR/KITCHEN`.
- Set item `QUEUED`.
- Emit `kds_new_ticket`.
- Idempotent khi bấm submit nhiều lần.

## 4. Kitchen status

### `PATCH /api/v1/orders/:id/items/:itemId/kitchen-status`

- Role: `STAFF`, KDS role nếu có.
- Validate `QUEUED -> PREPARING -> READY -> SERVED`.
- Cho phép CANCELLED theo rule.
- Emit `kds_item_status_changed`.
- Khi tất cả item served, cập nhật order status phù hợp.

## 5. Thanh toán order

### `POST /api/v1/orders/:id/pay`

- Role: `STAFF`, `CUSTOMER` theo ownership.
- Nhận `payment_method`:
  - [ ] `VIETQR`.
  - [ ] `WALLET`.
  - [ ] `COFFEE_PASS`.
- Tính lại amount từ database.
- Idempotency key.
- Ghi payment transaction.
- Wallet gọi `fn_pay_order` do B1 tạo; không tự ghép nhiều update Supabase.
- Coffee Pass kiểm tra subscription và redemption.
- Thành công chuyển order `COMPLETED`.
- Trigger CDP chạy đúng.
- Emit order/table update.
- Ghi audit log.

## Tiêu chí nghiệm thu

Staff có thể check-in -> thêm món -> submit kitchen -> KDS xử lý -> thanh toán. Customer không thể sửa giá/tổng bằng payload. Bấm thanh toán lặp lại không trừ tiền hai lần.

# P3 - Group-order API

## `POST /api/v1/group-order/join`

- Role: `CUSTOMER`.
- Kiểm tra table đang `OCCUPIED`.
- Tạo/nhận session Redis theo `tenant_id` và `table_id`.
- Trả session/member/cart.
- Không cho cross-tenant join.

## `GET /api/v1/group-order/:tableId/cart`

- Role: `CUSTOMER`.
- Đọc session Redis.
- Nếu không có session trả `ERR_5001_SESSION_NOT_FOUND`.

## `POST /api/v1/group-order/:tableId/cart/items`

- Role: `CUSTOMER`.
- Kiểm tra product active.
- Ghi item, quantity, member info.
- Có concurrency protection.
- Emit `group_order_cart_updated` tới `group_order:{tenant_id}:{table_id}`.

## `POST /api/v1/group-order/:tableId/confirm`

- Role: `CUSTOMER`, `STAFF`.
- Lock session trước khi convert.
- Kiểm tra order mở.
- Ghi cart vào order_items.
- Submit kitchen.
- Nếu Postgres/KDS fail phải rollback hoặc mở lại session an toàn.
- Không mất cart khi downstream fail.
- Emit trạng thái confirmed.

## Reconnect

- Redis session có TTL rõ ràng.
- Socket reconnect gọi lại GET cart.
- Không duplicate item khi client retry.
- Test hai thiết bị cùng bàn.

# Quy trình xử lý nghiệp vụ bắt buộc

Phần này mô tả thứ tự trong service. B2 không chỉ tạo route cho có response; mỗi bước phải được thực hiện ở backend để frontend không thể tự bỏ qua kiểm tra.

## Reservation lock

1. Guard xác thực JWT và lấy `tenant_id`, `branch_id`, `user_id`.
2. Đọc table bằng user-scoped Supabase client.
3. Kiểm tra table thuộc branch/tenant và đang `AVAILABLE`.
4. Sinh reservation code và lock token server-side.
5. Gọi Redis `SET NX EX`; nếu key đã tồn tại trả `ERR_2002_TABLE_LOCKED`.
6. Cập nhật table sang `PENDING_LOCK` trong boundary an toàn.
7. Tạo reservation/payment intent nếu schema yêu cầu.
8. Chỉ sau khi mọi bước thành công mới trả `expires_at` và QR data.
9. Nếu database update thất bại sau khi Redis lock thành công, phải xóa lock để không giữ bàn mồ côi.
10. Khi timeout/hủy, compare-and-delete lock rồi mới đưa bàn về `AVAILABLE`.

Mục đích: ngăn hai khách cùng giữ một bàn và ngăn Redis/Postgres bị lệch trạng thái.

## Webhook payment

1. Kiểm tra secret/rate limit trước khi parse nghiệp vụ.
2. Validate amount, raw content và tenant identifier.
3. Dùng idempotency key hoặc unique index để nhận biết webhook lặp.
4. Tìm reservation theo code trong đúng tenant.
5. Nếu không khớp, ghi unmatched transaction và kết thúc, không tự đoán customer.
6. Nếu khớp, ghi payment transaction completed.
7. Chuyển table `PENDING_LOCK -> RESERVED` và giải phóng Redis lock.
8. Commit database trước khi emit event.
9. Emit `table_status_changed` hoặc `unmatched_transaction_created` sau commit.
10. Trả response cho webhook có cờ `idempotent` để dễ vận hành.

Mục đích: payment callback có thể đến nhiều lần hoặc sai nội dung, nên phải an toàn và truy vết được.

## Tạo order và thêm món

1. Xác thực actor và quyền tạo order.
2. Lock table/order context để không có hai nhân viên check-in cùng lúc.
3. Kiểm tra reservation/deposit nếu có.
4. Tạo order code và order ở trạng thái `PENDING`.
5. Gắn table, branch, tenant và customer đúng nguồn server-side.
6. Khi thêm item, đọc product hiện tại từ database.
7. Reject product inactive, quantity không hợp lệ hoặc modifier không hợp lệ.
8. Lưu snapshot tên/giá cần thiết cho lịch sử order.
9. Tính subtotal/final amount trên server.
10. Chỉ cho sửa item trước khi order submit kitchen.

Mục đích: frontend chỉ gửi lựa chọn món; backend mới là nguồn sự thật của giá, ownership và trạng thái order.

## Submit kitchen và KDS

1. Đọc order và lock nếu cần để tránh submit đồng thời.
2. Reject order rỗng bằng error code chuẩn.
3. Kiểm tra order đang ở trạng thái được submit.
4. Phân item theo `BAR` hoặc `KITCHEN` từ category/product.
5. Đặt kitchen status thành `QUEUED`.
6. Commit các thay đổi order trước.
7. Emit `kds_new_ticket` vào `kds:{branch_id}` sau commit.
8. Khi KDS cập nhật, validate state machine trước khi ghi.
9. Emit `kds_item_status_changed` sau khi update thành công.
10. Có endpoint snapshot để reconnect không phụ thuộc event đã bỏ lỡ.

Mục đích: món phải xuất hiện đúng trạm và không bị tạo ticket trùng khi staff bấm nhiều lần hoặc reconnect.

## Thanh toán order và wallet

1. Đọc order từ database, không nhận total cuối từ client.
2. Kiểm tra order thuộc customer/staff có quyền.
3. Kiểm tra order chưa completed/cancelled.
4. Tạo hoặc kiểm tra idempotency key.
5. Với wallet, khóa row wallet bằng transaction/RPC.
6. Trừ `promo_balance` trước, sau đó mới trừ `main_balance` nếu đúng rule.
7. Ghi wallet ledger cho từng phần balance bị trừ.
8. Ghi payment transaction và cập nhật order trong cùng boundary.
9. Trigger CDP chỉ được chạy sau order completed.
10. Audit actor, amount, method, order id và kết quả.
11. Emit event sau commit; không emit success nếu transaction rollback.

Mục đích: bảo vệ tiền, chống double charge và bảo đảm báo cáo/CDP khớp với order thật.

## Group-order

1. Xác thực customer và kiểm tra table đang có order mở.
2. Tạo session key theo tenant/table, không dùng table id đơn độc.
3. Ghi member/cart vào Redis với TTL.
4. Mỗi add item phải kiểm tra product active và dùng thao tác atomic phù hợp.
5. Emit cart update sau khi Redis ghi thành công.
6. Khi confirm, lock session để chỉ một client được convert.
7. Kiểm tra order id hiện tại của table.
8. Insert order items và submit kitchen.
9. Nếu Postgres hoặc downstream fail, khôi phục session chưa confirm và không xóa cart.
10. Reconnect phải đọc lại cart từ Redis, không tin state cũ của browser.

Mục đích: nhiều người cùng bàn có thể gọi món mà không mất dữ liệu hoặc ghi item hai lần.

## Coffee Pass

1. Kiểm tra plan thuộc tenant và còn active.
2. Kiểm tra customer có wallet và đủ số dư.
3. Khóa wallet.
4. Trừ tiền atomically.
5. Tạo subscription và số lượt dùng.
6. Sinh secret TOTP an toàn, chỉ lưu server-side.
7. Khi redeem, verify subscription, expiry, TOTP window và rule mỗi ngày.
8. Lock subscription để chống redeem đồng thời.
9. Trừ lượt và ghi audit.

Mục đích: subscription và lượt dùng không thể bị nhân đôi bằng cách gửi request song song.

## Support và Maker-Checker

1. Support đọc unmatched trong tenant của mình.
2. Fuzzy match chỉ trả candidate có scope hợp lệ.
3. Maker tạo proposal và ghi `maker_user_id`.
4. Checker phải khác maker và có role phù hợp.
5. Backend kiểm tra lại trạng thái proposal ngay trước approve.
6. Mutation payment/customer/order chạy trong transaction.
7. Ghi audit trước/sau và actor.
8. Commit thành công mới emit support event.
9. Resolve ticket phải lưu kết quả và voucher nếu có.
10. Merge customer phải kiểm tra cùng tenant và bảo toàn wallet/order/history.

Mục đích: phân tách người đề xuất/người duyệt và bảo vệ các thao tác tài chính có rủi ro cao.

# Các Nhiệm vụ bổ sung (Shift, Takeaway, Inventory)

## 1. Quản lý Ca làm việc (Shift)
- [ ] Viết API Mở ca (`POST /api/v1/shifts/open`) với số tiền đầu ca.
- [ ] Viết API Đóng ca (`POST /api/v1/shifts/close`), tính toán tiền mặt dự kiến dựa trên các order đã thanh toán bằng tiền mặt trong ca.
- [ ] Middleware/Guard chặn nhân viên thanh toán order nếu chưa mở ca (tùy config).
- [ ] **(Đồng bộ Gap 2)** Khi tạo mới order (`POST /api/v1/orders`), API phải tự động mapping `shift_id` của ca làm việc đang mở vào order.

## 2. Đơn mang đi (Takeaway / Delivery)
- [ ] Cập nhật logic `POST /api/v1/orders`: Xử lý riêng flow khi `order_type` là `TAKEAWAY` (không cần kiểm tra `table_id` và trạng thái bàn).
- [ ] Quản lý queue cho đơn Takeaway tại KDS.

## 3. Quản lý Kho & Định lượng (Inventory)
- [ ] Viết logic trừ kho (Inventory Deduction) tự động: Lắng nghe event khi order chuyển sang `COMPLETED`, tìm recipe của các món và trừ số lượng `ingredients` tương ứng.
- [ ] API Nhập/Xuất kho thủ công, xem tồn kho hiện tại cho Admin.
- [ ] **(Đồng bộ Gap 3)** Trigger event qua Socket (`product_out_of_stock`) ngay khi số lượng nguyên liệu trừ về 0 để POS/App tự động khóa món.
