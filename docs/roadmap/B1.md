# B1 - Database, Supabase và Backend Core

## 1. Vai trò

B1 là người phụ trách dữ liệu Supabase và nền tảng backend. B1 chịu trách nhiệm trực tiếp với schema, migration, RLS, JWT claims và các API nền tảng. Không thành viên nào tự sửa schema Supabase dùng chung mà không qua B1.

## 2. Phạm vi sở hữu

- Supabase project và biến môi trường backend.
- Database migrations.
- ERD, index, constraint, trigger, function.
- RLS và tenant isolation.
- Supabase Auth custom access token hook.
- Guard, decorator, response envelope và error handling dùng chung.
- API Auth.
- API Floor/Table.
- API Menu.
- API Staff.
- API CDP/Reports.
- Seed SQL nền tảng và dữ liệu reference.

## 3. Quy tắc bắt buộc

- Không dùng `service_role` key trong request path thông thường.
- Query nghiệp vụ phải forward JWT của request qua `SupabaseService.forUser()`.
- Mọi schema change phải là migration đánh số.
- Sau mỗi migration phải cập nhật ERD/RLS/API contract nếu contract thay đổi.
- Không tạo role mới chỉ ở frontend.
- Không xóa cứng product đã được order tham chiếu.
- Mọi bảng tenant-scoped phải có boundary RLS.

# P2 - API nền tảng B1 phải hoàn thành

## 1. Auth API

### `POST /api/v1/auth/register`

- Public.
- Nhận tenant/subdomain và thông tin customer hợp lệ.
- Tạo Supabase Auth user.
- Tạo `customers`.
- Tạo wallet rỗng.
- Không nhận hoặc tin field `role` từ client.
- Trả response envelope và session phù hợp.

### `POST /api/v1/auth/login`

- Public.
- Xác thực email/password hoặc phương thức đã chốt.
- Trả access token/refresh token.
- Claims phải đúng tenant và role.

### `POST /api/v1/auth/refresh`

- Public.
- Cấp access token mới.
- Từ chối refresh session bị revoke/inactive nếu business rule yêu cầu.

### `GET /api/v1/auth/me`

- Tất cả user đã đăng nhập.
- Trả profile tối thiểu, role, tenant, branch và trạng thái account.

## 2. Floor/Table API

### `GET /api/v1/floors?branch_id=`

- Role: `OWNER`, `STAFF`, `CUSTOMER`.
- Trả floor thuộc branch và tenant hiện tại.

### `POST /api/v1/floors`

- Role: `OWNER`.
- Tạo floor với name, level, background nếu có.

### `GET /api/v1/floors/:id/tables`

- Role: `OWNER`, `STAFF`, `CUSTOMER`.
- Trả `id`, `table_code`, `capacity`, `pos_x`, `pos_y`, `width`, `height`, `shape`, `status`, `current_order_id`.

### `POST /api/v1/tables`

- Role: `OWNER`.
- Validate floor thuộc tenant.
- Validate capacity, shape và tọa độ.

### `PATCH /api/v1/tables/:id`

- Role: `OWNER`.
- Dùng cho Floor Editor.
- Cho sửa table code, capacity, `pos_x`, `pos_y`, width, height, shape.
- Không cho đổi `floor_id` nếu contract chưa cho phép.

### `PATCH /api/v1/tables/:id/status`

- Role: `STAFF`.
- Validate state machine: cleaning/available và các chuyển đổi hợp lệ.
- Không cho staff tự chuyển trạng thái trái quy trình.

## 3. Menu API

### `GET /api/v1/categories`

- Role: `OWNER`, `STAFF`, `CUSTOMER`.
- Trả category theo tenant.

### `GET /api/v1/public/catalog?tenant_subdomain=&branch_id=`

- Public, không cần JWT.
- Đây là endpoint duy nhất cho khách vãng lai xem menu.
- Resolve tenant bằng `tenant_subdomain`; nếu có `branch_id` phải kiểm tra branch thuộc tenant.
- Chỉ trả category/product active và các field public đã chốt.
- Không trả dữ liệu quản trị, cost, audit hoặc customer data.
- Không cho anonymous ghi bất kỳ dữ liệu nào.

### `POST /api/v1/categories`

- Role: `OWNER`.
- Nhận name và `kitchen_station`.

### `PATCH /api/v1/categories/:id`

- Role: `OWNER`.

### `DELETE /api/v1/categories/:id`

- Role: `OWNER`.
- Không xóa nếu còn product active.

### `GET /api/v1/products?category_id=`

- Role: `OWNER`, `STAFF`, `CUSTOMER`.
- Customer chỉ thấy product active.

### `POST /api/v1/products`

- Role: `OWNER`.
- Nhận name, price, category, modifiers mặc định; chỉ nhận `image_url`/`description` sau khi migration và API contract đã được cập nhật.

### `PATCH /api/v1/products/:id`

- Role: `OWNER`.
- Hỗ trợ đổi giá, tên, modifiers, active state.

### `DELETE /api/v1/products/:id`

- Role: `OWNER`.
- Soft delete bằng `is_active = false`.

## 4. Staff API

### `GET /api/v1/staff?branch_id=`

- Role: `OWNER`.
- Trả staff/support của branch/tenant.

### `POST /api/v1/staff`

- Role: `OWNER`.
- Backend tạo Supabase Auth user bằng Admin API.
- Tạo profile `users` qua flow an toàn.
- Trả temporary credential một lần nếu môi trường demo.
- Không nhận `auth_user_id` từ client.

### `PATCH /api/v1/staff/:id`

- Role: `OWNER`.
- Sửa tên, phone, role, branch, active state theo rule.

### `PATCH /api/v1/staff/:id/deactivate`

- Role: `OWNER`.
- Không deactivate Owner cuối cùng.
- Không cho session mới của account inactive.

## 5. CDP/Reports API

### `GET /api/v1/cdp/customers?segment=`

- Role: `OWNER`, `SUPPORT`.
- Phân khúc VIP, loyal, churn risk, new.

### `GET /api/v1/cdp/customers/:id/360`

- Role: `OWNER`, `SUPPORT`.
- Trả lịch sử chi tiêu, visits, tier, món yêu thích, ghi chú dị ứng.

### `GET /api/v1/reports/dashboard?branch_id=`

- Role: `OWNER`.
- Trả revenue, order count, occupied tables, top products, payment breakdown.

### `POST /api/v1/cdp/customers/:id/vouchers`

- Role: `OWNER`, `SUPPORT` nếu contract cho phép.
- Tạo voucher có expiry, rule và audit.

## Tiêu chí nghiệm thu API

- API thật chạy với JWT thật.
- Response đúng envelope.
- DTO reject dữ liệu sai.
- Error code khớp tài liệu.
- RLS không lộ dữ liệu khác tenant.
- FE có thể bắt đầu tích hợp mà không cần mock response.

## RPC tài chính bắt buộc bàn giao cho B2

### `fn_pay_order`

B1 phải tạo migration và function `SECURITY DEFINER` để cập nhật order, payment transaction, wallet ledger và số dư trong cùng một transaction database.

1. Nhận order id, actor/customer id, payment method và idempotency key.
2. Kiểm tra order thuộc đúng tenant và actor có quyền.
3. Khóa order và wallet nếu payment dùng wallet.
4. Tính amount từ order trong database, không nhận final amount tin cậy từ client.
5. Trừ `promo_balance` trước `main_balance`.
6. Ghi từng wallet transaction cần thiết.
7. Cập nhật payment transaction và order `COMPLETED` atomically.
8. Trả kết quả idempotent nếu request đã xử lý trước đó.
9. Ghi audit log hoặc trả dữ liệu đủ để B2 ghi audit theo contract.

B2 chỉ được gọi function này; B2 không tự ghép nhiều request Supabase để giả lập transaction.

## Quy trình thực hiện từng nhóm API

### Auth: làm gì và vì sao

Auth là điểm gốc của toàn bộ phân quyền. Nếu claims sai, mọi API phía sau có thể đọc sai tenant hoặc role.

1. Kiểm tra user tồn tại trong Supabase Auth.
2. Kiểm tra user có profile đúng trong `users` hoặc `customers`.
3. Khi login/refresh, chạy custom access token hook để lấy role, tenant và branch từ profile server-side.
4. Đảm bảo client không thể gửi `role`, `tenant_id` hoặc `branch_id` để tự nâng quyền.
5. Backend verify chữ ký JWT trước khi gọi service.
6. Test `/auth/me` bằng từng tài khoản Owner, Staff, Support và Customer.
7. Ghi rõ response mẫu và lỗi mẫu cho frontend.

Kết quả bàn giao: frontend chỉ cần token thật và có thể biết chính xác user đang là ai, thuộc tenant/branch nào.

### Floor/Table: làm gì và vì sao

Floor/Table là nguồn dữ liệu cho đặt bàn, POS và Floor Editor. Vị trí phải lưu ở database để mọi thiết bị nhìn thấy cùng một layout.

1. Load floor theo `branch_id` đã được kiểm tra trong JWT/RLS.
2. Load tables theo `floor_id`.
3. Trả cả thông tin hình học (`pos_x`, `pos_y`, `width`, `height`, `shape`) và trạng thái vận hành.
4. Khi Owner tạo/sửa layout, validate floor/table cùng tenant.
5. Khi Staff đổi status, chỉ cho phép transition hợp lệ.
6. Không cho customer update vị trí hoặc status trực tiếp.
7. Test hai token ở hai tenant khác nhau để xác nhận query trả mảng rỗng hoặc forbidden đúng contract.
8. Ghi ví dụ payload cho F1 dùng ở Floor Editor và F2 dùng ở customer floor map.

Kết quả bàn giao: frontend không phải tự tạo `INITIAL_TABLES` hoặc tự tính vị trí theo index.

### Menu: làm gì và vì sao

Menu là dữ liệu public được đọc nhiều nhưng chỉ Owner được sửa. Product phải soft-delete để không làm hỏng order history.

1. Validate category thuộc tenant hiện tại.
2. Validate `kitchen_station` để B2 có thể phân luồng KDS.
3. Khi đọc cho Customer/public, chỉ trả product active.
4. Khi đọc cho Owner, có thể trả cả product inactive để quản trị.
5. Khi sửa giá/tên, không sửa snapshot của order cũ.
6. Khi xóa product, chuyển `is_active = false` thay vì delete cứng.
7. Khi xóa category, kiểm tra còn product active hay không.
8. Test Customer, Staff và Owner nhận đúng tập dữ liệu khác nhau.

Kết quả bàn giao: F2 có menu thật, B2 có product/category ổn định để tính order và tách KDS.

### Staff: làm gì và vì sao

Staff API tạo danh tính vận hành, nên phải tránh Auth user mồ côi hoặc profile không có role.

1. Owner gửi email, tên, phone, role và branch.
2. Backend validate role/branch và kiểm tra trùng phone/email.
3. Supabase Admin API tạo Auth user với mật khẩu tạm.
4. Insert profile `users` bằng dữ liệu tenant của Owner, không lấy tenant từ client.
5. Nếu insert profile thất bại, xóa Auth user vừa tạo để tránh user mồ côi.
6. Chỉ trả mật khẩu tạm một lần ở môi trường demo.
7. Deactivate phải chặn Owner cuối cùng.
8. Test token cũ, token mới và lần refresh sau khi deactivate.

Kết quả bàn giao: F2 có thể quản lý staff thật và B2 có staff actor để test POS/KDS.

### CDP/Reports: làm gì và vì sao

CDP và report phục vụ Owner/Support, không được làm lộ dữ liệu customer không cùng tenant.

1. Tạo query read-only theo tenant/branch.
2. Xác định rõ khoảng thời gian và timezone khi tính doanh thu.
3. Tính phân khúc customer từ dữ liệu order đã completed.
4. Trả dữ liệu tổng hợp có pagination khi danh sách lớn.
5. Không cho frontend tự tính lại số liệu chính thức.
6. Tạo voucher qua API có expiry và audit.
7. Test dữ liệu rỗng, ngày không có order và branch không có quyền.

Kết quả bàn giao: F2 có thể dựng Analytics và Customer 360 bằng response ổn định.
